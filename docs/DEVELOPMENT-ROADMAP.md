## 1. 产品方向与已确认事实

目标是一个统一的媒体归档、直播录制、自动处理与跨平台发布工作台。历史录播、实时录制和 UP 主投稿备份是三种素材来源，共用素材库、任务中心、处理节点和 YouTube 发布能力。

保留 Rust 核心 + Tauri 桌面壳 + Vue WebUI 的现有选择，逐步拆分现有模块，不重新推倒实现。

- 用户在本次沟通中确认：已经实际测试真实 YouTube 私密上传，结果可以接受。这项按「用户实测通过」记录；不再作为下一阶段的起点阻塞。
- 不据此推定：大量远端视频修改、播放列表写入、所有断线恢复场景和不同平台授权均已实测。
- 现有扫描、合并、切割、续传上传、批量元数据编辑、主题及 Windows 包继续作为回归基线。
- 这轮交付开发规划；后续再通过用户指定的本机 OAuth 配置/已有授权读取频道。没有在这轮读取凭据、同步频道或修改远端视频。
- 暂按个人/家庭单管理员设计。多频道数据应隔离；多人协作权限、分布式执行器不作为本轮依赖。
- Docker 先以 NAS/家用服务器部署为设计基线，同时预留域名 + HTTPS 的远程部署。具体优先环境待用户补充，不能假定远程浏览器能访问服务器的 localhost。

## 2. 现有代码对规划的影响

| 现状证据 | 对应调整 |
| --- | --- |
| `Config.library` / `Library.root` 为单一路径，启动时检查数据库属于同一个根目录 | 引入 LibraryRoot、素材独立身份及路径位置记录；已有单库迁移为默认根目录 |
| SQLite 目前仅 `documents(kind,id,json)`，素材和远端列表整批读取 | 增量迁移为带索引的实体表；大列表由服务端分页/筛选，保留原始元数据 JSON |
| `App.vue` 用单一 view 切换整页，`YouTube.vue` 集中账号、上传、队列与视频编辑 | 拆分路由页面、共用选择组件和详情面板；侧边栏分组可展开 |
| 素材选择行虽有小型「清除」入口，但底部浮动操作栏没有全局取消入口 | 固定批选工具栏明确「取消全部选择」，显示当前筛选之外的已选数量 |
| 本地 Job 与 UploadJob 是不同模型，YouTube 页轮询整个快照 | 先统一任务查询/展示，再迁移到共同的调度、事件与执行记录；避免重建已有上传会话 |
| Artifact 只保留 source_ids，缺少逐段输入/输出区间 | 引入版本化时间映射，为切片、弹幕、章节和补档共用 |
| 服务绑定 localhost，凭据依赖系统 keyring；桌面端口随机 | 增加 headless 配置与凭据后端；桌面设置不能仅靠随随机端口变化的浏览器存储 |
| 无项目自身的跨平台 CI；便携脚本仅打 Windows 包 | 从第一阶段建立多平台编译检查，再逐项交付各平台可安装、可运行的包 |

源文件定位：`app/crates/core/src/{lib,model,db,scanner,jobs,youtube,web}.rs`、`app/desktop/src/main.rs`、`app/web/src/{App,YouTube}.vue`。本节是源码检查结论，不表示这些改造已经完成。

## 3. 功能分组与交互规则

侧边栏一级功能可展开/折叠，每个子项是独立页面，支持链接直达、返回/前进、恢复筛选及滚动位置。

| 一级功能 | 子页面 |
| --- | --- |
| 工作台 | 概览、近期活动、待处理异常 |
| 媒体库 | 全部媒体、按场次浏览、文件夹来源、分组与保存视图、异常与重复候选 |
| 直播管理 | 直播间、正在录制、监控规则、录制历史、录制引擎 |
| YouTube | 频道视频、播放列表、上传准备、批量变更记录；账号连接从设置入口管理 |
| 工作流 | 模板、自定义流程、触发规则、运行记录 |
| 备份与补档 | UP 主订阅、源视频目录、差异与缺失、归档记录 |
| 任务中心 | 全部、运行中、等待/暂停、失败/待处理、已完成 |
| 设置 | 账号与连接、存储、外观、处理组件、资源限制、备份恢复、关于 |

交互要求：

1. 素材库与频道视频使用一致的多选模型：当前页、全部筛选结果、Shift 范围选择、反选、取消全部。全局取消指当前功能的整个选择集合，包含筛选后隐藏的条目，不联动清掉其他页面独立草稿。
2. 有选择时固定显示「已选 N / 当前可见 M / 隐藏 K」和「取消全部选择」；空筛选结果、翻页和窄窗口下也能操作。Esc 可取消选择，但不抢占输入法、编辑框或弹窗的退出行为。
3. 全选筛选结果在提交时冻结目标 ID 集合/查询版本，预览数量与执行数量可核对；同步期间新出现的视频不会悄悄加入已确认的修改。
4. 上传准备页只负责选媒体、填元数据、预览目标列表和提交。上传速度、进度、暂停、失败与重试统一进入任务中心；业务页保留任务摘要和跳转入口。
5. 批量变更走「选对象 → 配规则 → 看差异/冲突 → 执行 → 看逐项结果」。提供保存草稿和仅重试失败项，已成功条目不重复执行。
6. 上千视频采用服务端分页、稳定排序与虚拟列表；详情、单项编辑用侧栏，长配置拆成子页/分步流程。背景刷新不重置筛选和选择。
7. 每个阶段持续检查键盘操作、焦点、明暗主题、对比度、空状态、加载/错误状态；外观偏好在桌面重启和服务端口变化后仍保留。

## 4. 八项需求的具体范围

### 4.1 跨平台桌面与 Docker headless

| 目标 | 计划产物 | 必须有的验收证据 |
| --- | --- | --- |
| Windows x64 | 便携目录、NSIS 安装包 | 干净环境运行、升级/卸载不误删媒体、内置工具调用 |
| macOS Apple Silicon / Intel | 对应架构 app / DMG；两架构独立验收后再考虑 universal | 安装、文件访问、Keychain、OAuth、内置媒体工具与签名/公证流程 |
| Linux x64 / arm64 | 分架构 deb；AppImage 按架构依赖情况验收，后续补其他包格式 | 约定发行版基线、WebView 依赖、凭据持久化、字体、实际媒体处理 |
| Docker linux/amd64 + linux/arm64 | 多架构镜像、Compose、健康检查及升级说明 | 无桌面/无显示服务器运行、浏览器连接、卷持久化、重启恢复、停止时回收子进程 |

各目标需要各自的 FFmpeg/FFprobe，以及对应功能所需的下载器、弹幕工具、字体和运行时。开发可用系统工具，发行包和镜像提供固定版本、校验和、能力清单；不能在 ARM 包里混入 x64 工具。构建成功与功能验收分开显示。

从下一阶段就建立 GitHub Actions 编译与打包矩阵；Release 包、SHA-256、版本说明和容器清单在相应平台验收后发布。先提供手动升级和数据库备份恢复，再安排签名自动更新。Tauri 的分发和 macOS 签名/公证按官方流程实现。[Tauri 分发](https://v2.tauri.app/distribute/)、[macOS 签名与公证](https://v2.tauri.app/distribute/sign/macos/)、[Docker 多架构构建](https://docs.docker.com/build/building/multi-platform/)

Docker 设计：

- Rust 服务直接托管 WebUI；不依赖 Tauri、X11 或宿主机浏览器。
- 区分 `/data` 数据库配置、`/media/<root>` 素材挂载、`/recordings` 录制输出、`/downloads` 下载暂存、`/exports` 成品。用户导入的历史素材默认只读；录制/下载目录显式可写。
- 增加监听地址、外部访问地址、受信代理/来源配置、单管理员登录和服务端会话。目录选择器浏览的是授权的服务器目录，不是浏览器所在电脑。
- 桌面 OAuth 保留本机回调；部署在服务器上的 Web 版使用对应 Web OAuth 客户端和注册的 HTTPS 回调。JSON 客户端配置本身不等于用户授权。
- 无域名的纯局域网安装，先验证管理员通过 SSH 本机端口转发完成初始授权的方案，或提供受认证的桌面授权辅助流程；在实际打通前标为待验收。不能依赖已废弃的复制授权码 OOB 方案，也不能把容器内 localhost 当成访问者的 localhost。[Web OAuth](https://developers.google.com/identity/protocols/oauth2/web-server)、[OOB 迁移说明](https://developers.google.com/identity/protocols/oauth2/resources/oob-migration)
- 抽象凭据存储：桌面使用系统凭据服务，headless 使用持久化加密存储和独立挂载的密钥；首次配置、重启后解锁/自动解锁、备份恢复和密钥轮换都要可操作。
- 容器以非 root 用户运行；健康检查、SIGTERM 优雅退出、日志轮转、资源限制进入验收。SQLite 数据目录使用可靠的本地卷；远端 NAS 媒体挂载掉线不能判为文件已删除。

### 4.2 多文件夹媒体库与录制目录识别

- 一个媒体库可添加多个根目录，分别配置显示名、时区、来源类型、排除规则、只读/可写和监控策略；支持批量导入。
- 建立来源适配器：现有 LiveRec、BililiveRecorder、biliLive-tools、普通视频目录、后续 yt-dlp 元数据。识别依据包括录制信息 XML、配置/记录、目录结构和文件名；保存证据、置信度与解析器版本。
- 使用实际样本建立格式测试集，支持格式自动识别 + 手工指定；未知格式仍可作为普通媒体入库。biliLive-tools 可自定义命名，不能把某一种文件名模板当成全部支持。
- 多根目录同名文件不冲突；根目录迁移/重新挂载可重新关联。重叠根目录、符号链接/目录连接循环、大小写及 Unicode 差异需处理。
- 文件状态区分：正在增长、稳定、已变更、缺失、根目录离线、待确认重复。离线盘不触发整库删除；移动识别保留人工确认入口。哈希用于确认内容，不把文件名/mtime 当成唯一身份。
- 增量扫描与目录事件结合；网络挂载事件不可靠时定期补扫。录制结束通知结合文件稳定检测再触发后处理。
- XML/TXT/封面/弹幕/字幕独立登记，允许只有旁文件而视频缺失。保存媒体与本地成品、远端视频的多对多来源关系。
- 显示标题、磁盘文件名、YouTube 标题分别编辑。文件系统批量重命名作为后续可选操作，预览重名/非法字符，同时更新关联旁文件与索引，并保留失败恢复记录；普通命名规则默认作用于显示标题或新成品。
- 从导入资料生成「待加入直播管理的房间」：平台 + 真实房间 ID 去重，主播 UID、房间 ID、短号、别名分开存。导入向导列出匹配和冲突，可批量启用监控/录制；历史元信息不被在线当前标题覆盖。

### 4.3 直播管理与录制引擎

- 在本软件中提供房间监控、直播状态、录制开始/停止、画质、路径模板、重试与录制历史。
- 先适配现有 biliLive-tools 服务，验证完成后再提供随包受管运行；Docker 可用独立 recorder 服务，通过 API 和事件连接 Rust 核心。
- BililiveRecorder 第一阶段支持目录/元信息导入及结束事件适配；直接控制该引擎需单独验证其版本与接口，不以目录识别代表已经支持录制控制。
- 录制任务进入同一个任务中心，显示时长、速度、文件数和磁盘占用，长期录制不伪造百分比。录制完成触发文件导入及指定工作流。
- 每个房间确定执行录制的引擎及任务归属；避免两个引擎重复录制、两套后处理同时上传。事件持久化、去重，周期性对账补偿漏通知。
- 首批验收 B 站；其他直播平台列出具体引擎和功能状态逐项扩展。可参考本地 `biliLive-tools/docs/api/recorder.md` 和 `docs/features/external-event.md`，对可能滞后的文档以固定版本实际接口为准。

### 4.4 上千条 YouTube 视频的调研与批量管理

调研从下一阶段即可开展，不必等所有基础改造结束：

1. 用户指定应用实例/频道后，优先复用该实例已有授权；需要新配置时在本机导入 OAuth JSON。核对授权对应的频道 ID，读取阶段只调用查询接口。
2. 读取频道 uploads 列表，分页取全量视频 ID，再分批取视频详情；同时分页读取自建播放列表及成员关系。保存同步时间、范围、遗漏/不可读项和原始快照。
3. 分析标题格式、UP 主/房间号线索、日期与期数、描述模板、标签、隐私、时长、缺失封面/字幕线索、列表覆盖、重复候选、本地与云端关联。发布时间与录制时间分列；文件细节/分辨率仅在 API 可返回时使用，缺失保留未知。
4. 输出「频道盘点报告 + 典型命名样例 + 批处理候选及影响数量 + 规则草案」。区分确定提取、推断匹配与待确认，不在查看数据前臆测用户现有命名混乱情况。
5. 从真实频道样本选择 3–5 条最高价值规则，再进入批处理实现和小批验收。原始快照留本机，不把私密视频清单或授权数据提交 Git。

视频和播放列表查询以 Data API 资源为准。[视频详情查询](https://developers.google.com/youtube/v3/docs/videos/list)、[播放列表成员查询](https://developers.google.com/youtube/v3/docs/playlistItems/list)

优先候选功能：

- 按主播、房间、来源平台、录制日期、画幅、时长、标题模式、隐私、列表归属和本地匹配状态筛选；保存智能视图。
- 无需正则的规则积木：统一日期、清理录制前缀、补主播/房间号、期数/分片编号、标题查找替换、描述公共区块、原站链接、标签增删去重。
- 标题、描述、标签、公开状态等字段的统一差异预览；批量修改保留未编辑字段并检测预览后发生的远端修改。
- 本地录像/成品与已有远端视频的关联建议；支持人工绑定/解除，避免只根据相同标题自动断定重复。
- 批量加入/移出播放列表、按录制时间/期数排序、缺失归档清单、JSON/CSV 导出、失败项重试。
- 后续增量：封面和字幕上传、定时发布等 API 可用能力。远端删除独立设计；不能承诺 Data API 覆盖全部 Studio 操作。

同步与写入分开排队。配额预算按动作和具体项目维护，耗尽时进入等待并可跨日续跑。例如当前官方方法页列明：创建播放列表和插入成员各为 50 units，单是给 1,000 条视频各添加一个列表成员就约 50,000 units，不能把「批量」设计成一次请求全部完成。成本、核对日期和估计剩余额度可见，实际以 Google 项目配额和返回结果为准。[配额](https://developers.google.com/youtube/v3/determine_quota_cost)、[创建播放列表](https://developers.google.com/youtube/v3/docs/playlists/insert)、[插入列表成员](https://developers.google.com/youtube/v3/docs/playlistItems/insert)

### 4.5 根据元信息自动归入播放列表

实现为可独立调用的「确保播放列表」和「加入播放列表」处理节点，同时服务新上传和历史视频整理。

- 主键建议为 `目标频道 + 来源平台 + 主播 UID/真实房间 ID + 规则范围`。昵称仅作显示，允许按年度/系列细分。
- 首先查询本地绑定的 playlist ID 并核验；没有绑定时分页获取该频道已有列表，根据已知 ID、明确的房间标识及用户规则匹配；多候选时等待确认，不凭昵称近似自动合并。
- 用户启用「不存在时自动创建」后，按模板创建列表并立即保存绑定。列表隐私单独配置，不因加入列表自动改变视频隐私。
- 插入成员前检查已有成员；同一房间的并发任务串行确保列表存在，避免同时新建。远端成功但响应丢失时先查询核实再重试，状态不明时不盲目创建。
- 上传取得 video ID、处理状态核验、加入列表、封面/字幕等是独立步骤。列表失败只重试列表步骤，不再次上传视频。
- 主播改名、列表被外部改名/删除、用户切换频道均可重新解析和修复绑定。

`playlists.list(mine=true)` 可读取已授权用户拥有的播放列表，再通过创建和成员接口完成上述能力。[读取自己的播放列表](https://developers.google.com/youtube/v3/docs/playlists/list)

### 4.6 可自定义的自动化工作流

先做可拖动排序的步骤列表和成熟模板，再加入分支/汇合的画布。底层从开始就保存节点、连接、类型和版本，后续不换一套执行引擎。

节点分组：

| 分组 | 首批节点 |
| --- | --- |
| 输入 | 指定素材/文件夹、录制完成、UP 主新增视频、手动/定时触发 |
| 识别与分组 | 探测、元信息提取、场次识别、按分辨率/画幅分类、去重候选 |
| 媒体处理 | 兼容片段合并、限时长/体积切割、转封装、统一规格转码、输出验证 |
| 元数据 | 命名规则、本地分组、标题/描述/标签模板、章节草稿；后续可选 AI 建议 |
| 弹幕/字幕 | 时间映射、过滤去重、XML/ASS/SRT 输出、HTML 预览、可选压制 |
| 发布与归档 | 上传准备、YouTube 上传/处理核验、确保列表/插入成员、封面/字幕、归档登记 |

执行要求：

- 每个节点声明输入输出类型、配置 schema、版本、所需资源、是否支持暂停、重试策略和恢复点。UI、手工单步执行与工作流调用同一能力。
- 开始前做类型/顺序校验、目标预览、空间和配额预算；保存不可变输入与规则快照。修改模板不会改变正在运行的实例。
- 统一 Run / Task / Attempt / Artifact / Event。一个流程有多个子任务，任务中心展开追踪，失败从需要重做的节点恢复，不重传已完成媒体。
- 对录制事件、下载来源和上传目标建立稳定去重键；并发限制覆盖 CPU/GPU、磁盘、录制、下载、上传和 API 配额。
- 跳过、重试、等待凭据/配额、需要确认、结果待核实都是可见状态。媒体百分比、上传字节、API 项目数按自己的单位展示。
- 流程先支持手动触发，再接录制完成、文件稳定和订阅更新，最后补定时；触发去抖、事件去重和失败重放同步交付。
- 初始模板使用规则生成元数据；AI 作为可替换节点，产出结构化建议并经过同一验证器，不成为基础工作流的必需依赖。

三个验收模板：

1. 历史录播：选场次 → 连续兼容段分组 → 合并/必要时切割 → 命名 → 弹幕同步 → 验证 → 私密上传 → 自动归列表。
2. 直播录制：导入房间并启用监控 → 开播录制 → 文件稳定入库 → 指定模板 → 统一任务结果。
3. 投稿备份：指定 UP 主 → 枚举投稿 → 增量下载 → 保存元信息/封面/字幕 → 必要的转封装或切割 → 验证 → 发布并归列表。

### 4.7 弹幕随视频合并、切割及预览

时间轴是先决条件：每个输出保存多段 `源素材 ID、源起点、源终点、输出起点、播放速率、时间依据`。一条源弹幕在选中区间内时，转换为 `输出起点 + (源弹幕时间 - 源起点) / 播放速率`；超出区间的内容不进入该输出。

- 按每一段映射处理断档、重叠、剪掉的片段、横竖屏重排和跨文件切割，不能仅按各文件名日期或时长累加。
- 规范化事件保留相对时间、可用的绝对时间、文本、模式、颜色、类型和来源。保留普通弹幕/醒目留言/礼物等差异，并允许配置哪些类型参与输出。
- 输出合并后的 XML/事件数据、ASS、SRT，以及 HTML + 数据的回放预览。ASS 支持排布与样式；SRT 作为按时间显示的文本记录，会丢失滚动轨道和样式，界面明确表示。
- HTML 预览支持视频同步、跳转、密度、关键词过滤及导出；导出的预览包明确媒体路径/选择方式，弹幕内容按文本转义，不作为脚本执行。
- 优先评估现有 biliLive-tools 的 DanmakuFactory 适配。现有模块已提供 XML→ASS 和播放数据接口；SRT 与独立 HTML 输出仍需实现和验收，不能把它们列为现有能力。
- 跨平台包和 Docker 提供可用字体及回退；画幅、字号、安全区域按输出规格计算。压制弹幕会生成新的媒体成品，和外挂字幕分开选择。
- 用带时间标记的样本验证边界弹幕、被裁区间、长时轴、重复时间戳、emoji/中文、横→竖→横、时区冲突及损坏 XML；输出必须能映射回原事件。

本地依据：`biliLive-tools/docs/features/danmaku-convert.md`、`biliLive-tools/docs/api/danma.md`。字幕上传作为独立 YouTube 节点接入，ASS 动态弹幕不能承诺在 YouTube 上按原样呈现。[字幕上传 API](https://developers.google.com/youtube/v3/docs/captions/insert)

### 4.8 UP 主投稿备份与补档

把 yt-dlp 封装为内容源适配器和下载执行器，和实时直播录制并列接入。

- 输入 UP 主主页/UID、合集或视频 URL；先枚举目录并展示总数、可访问项和失败项，再按日期、分 P、格式、体积及已归档状态筛选。目标支持首次全量和后续增量。
- 固定版本验证 B 站投稿枚举能力；平台接口、账号状态或提取器变化时可替换实现。不能把下载单个视频成功等同于完整枚举 UP 主全部投稿。
- 保存平台、UP 主 UID、BV/AV、CID/分 P、原 URL、原发布时间、描述、封面、可取得的字幕/弹幕、下载格式及工具版本。不同分 P 独立追踪。
- 下载采用结构化输出和参数数组；支持暂停/取消/重试、限速、网络代理和断点恢复。容器中的登录凭据由用户显式配置，不能假定能读取访问者浏览器的 Cookie。
- 使用下载归档机制辅助增量，并由本软件记录 `来源项 → 下载 → 验证成品 → YouTube video ID → 播放列表`。下载成功与备份完成分别记账。
- 现有兼容视频无需强行先合并：新增「导入现成视频并验证」路径，使下载视频直接成为合格上传候选。
- 404、权限不足、访问限制、私密/删除等分别记录，不无限重试；补档处理已有或仍可访问的文件，不能承诺取回不可取得的原片。
- 后续更新订阅时只调度未完成项；源视频删除不会自动删除本地备份或 YouTube 版本。源元数据变化可生成更新建议。
- 模板支持源作者、标题、发布日期、BV/分 P、原站链接，默认私密上传；用户配置发布范围与自动触发规则。保留来源和授权备注。

yt-dlp 已有下载归档和元数据 JSON 输出，可作为适配器基础；本软件仍需自己的任务状态与跨站映射。[yt-dlp 官方说明](https://github.com/yt-dlp/yt-dlp)

## 5. 数据与模块改造顺序

共享核心先建立五类稳定接口：素材来源、录制引擎、媒体处理节点、发布目标、凭据存储。第一轮使用内部接口和固定组件，不需要先开发通用插件市场。

| 数据域 | 关键实体 |
| --- | --- |
| 素材与历史 | LibraryRoot、MediaAsset、AssetLocation、Sidecar、Creator、Room、Session、Artifact、TimelineMap |
| 执行 | Task、TaskAttempt、TaskEvent、ResourceReservation、WorkflowDefinition/Version、WorkflowRun/NodeRun |
| 平台与发布 | ChannelConnection、RemoteVideo、RemotePlaylist、PlaylistBinding、PlaylistMembership、ChangeSet、UploadSession |
| 内容源 | SourceSubscription、SourceItem、DownloadRecord、PublicationMapping |

迁移原则：

1. 备份现有库，建立单调递增的 schema 版本和事务迁移；不能像当前初始化那样每次固定写 user_version=1。
2. 把现有唯一 library 变成一个 root，保留 asset/plan/output ID 或建立明确映射；已有标题、分组、验证记录、上传会话及远端 ID 不丢失。
3. 先通过任务适配层统一展示，再逐项迁移执行器；现有运行中的任务按明确策略排空/恢复。
4. 索引字段入关系表，原始平台/录制器 JSON 作为证据保留；列表接口分页，进度走任务事件和可恢复快照，避免反复传输整个频道。
5. 回退使用旧程序和对应迁移前备份；不承诺旧程序可以直接打开新 schema。用现有 v0.3.1 数据副本验收迁移。

## 6. 实施阶段与验收门槛

版本号为建议；用交付结果决定是否进入下一阶段，不在平台资源和真实数据量未知时承诺固定日期。

| 阶段 | 建议版本 | 核心交付 | 进入下一阶段的标准 |
| --- | --- | --- | --- |
| A：交互与执行基础 | v0.4 | 展开式侧栏、分页面、统一选择工具栏、合并/上传统一任务视图；跨平台 CI 骨架、headless OAuth 调研、频道只读盘点 | 多页/跨筛选取消选择正确；离开 YouTube 页仍能管理上传；老任务能查询/恢复；形成实际频道规则报告或明确待授权状态 |
| B：多来源素材基础 | v0.5 | 数据迁移、多根目录、来源适配、场次/路径身份、房间导入、时间映射；基础处理节点接口 | 两种录制目录混合导入、重叠根目录去重、离线盘/移动恢复、旧数据无损迁移；时间映射覆盖合并与切割 |
| C：跨平台与无界面运行 | v0.6 | macOS/Linux 桌面、Docker 两架构、服务配置/登录/凭据后端、打包分发 | 每个承诺平台在独立环境完成安装→导入→处理→授权/上传；headless 重启保留凭据和任务；原片与输出路径正确 |
| D：频道管理与自动归档 | v0.7 | 基于真实频道的批处理、播放列表、元数据补全、统一发布阶段与配额调度 | 上千视频分页可用；差异预览和冲突检测；已有/新建/同名冲突/重复成员/响应丢失均不造成重复发布；只重试失败步骤 |
| E：工作流与弹幕 | v0.8 | 可排序步骤、模板/版本、节点重试、XML/ASS/SRT/HTML、时间轴预览 | 历史录播模板可完整运行；弹幕在合并和切割后同步；失败恢复不重复上传；明暗界面与容器字体可用 |
| F：直播管理接入 | v0.9 | 房间监控、biliLive-tools 引擎、录制历史、结束事件触发流程 | 至少一个真实 B 站房间完成监控→录制→入库→后处理；重连/事件重复/进程重启不生成重复任务 |
| G：投稿备份与补档 | v0.10 | yt-dlp 来源、UP 主全量/增量目录、下载、分 P、备份映射、缺失对账 | 一个指定 UP 主完成枚举和代表样本发布；再次运行跳过已完成项，续做失败项；全量缺口可解释 |
| H：产品稳定与扩展 | v1.0 候选 | 图形化分支流程、可选 AI 节点、升级/恢复、性能与长时间运行 | 三个工作流模板跨目标平台回归；大库迁移和故障恢复通过；各平台发行材料与能力说明一致 |

节奏：A 中立即启动跨平台构建验证和真实频道研究；C 的构建基础可与 B 同步推进。D 的规则由频道盘点决定；E 的弹幕依赖 B 的时间映射；F/G 共用已经稳定的处理与发布节点。直播引擎接口在 B 设计，运行接入在 F 集中交付。

建议首个开发批次只锁定以下六项，以形成可审核的 v0.4：

1. 素材浮动工具栏增加明确的「取消全部选择」，补跨筛选计数。
2. 路由拆分；YouTube 首先拆成频道视频、播放列表占位/规划入口、上传准备，账号移入设置。
3. 任务中心聚合本地处理与上传，统一状态筛选、任务详情、进度及能力对应的操作。
4. 抽取共享列表选择和任务查询接口，保留现有执行器及上传恢复数据。
5. 建立 Windows/macOS/Linux 编译检查与 Docker 构建试验，尽早暴露系统依赖和 OAuth/凭据差异。
6. 用户提供具体实例后做频道只读盘点，交付批处理规则建议；不把某个账号暂未连接作为 UI 工作的前置阻塞。

## 7. 验收样本与规模

使用四组数据：现有 LiveRec；两种录制器的代表目录（默认/自定义命名、弹幕和分片）；用户上千条真实 YouTube 元信息；一个用户指定的 UP 主投稿清单。只读快照用于研究，远端写入先以用户选定的小批目标验收。

大库目标先以 10,000 个本地资产/远端缓存条目压测，在记录硬件与数据量后评估查询延迟、首屏响应、内存和批选正确性；不要求用户先全库转码才能验收。Docker 两架构、桌面目标系统分别记录工具版本、测试样本和结果。

代表故障覆盖：素材盘离线、文件被移动/仍在增长、空间不足、任务被终止、进度断流、凭据到期、API 配额耗尽、上传或列表写入成功但响应丢失、同一来源重复触发、多个账号切换。

## 8. 需要后续收敛的选择与发行事项

- Docker 的主要环境、首批 macOS/Linux 硬件及发行版、目标账号/频道数量、首个投稿备份对象，允许在对应阶段开始前补充。
- 媒体自动归档/清理、默认发布隐私、播放列表命名模板、AI 服务选型从真实用例确定；基础版本不依赖 AI。
- 检查到仓库根 `LICENSE` 为 Apache-2.0，而 `app/Cargo.toml` 和 `app/THIRD-PARTY-NOTICES.md` 声明 GPL-3.0-only；需要明确各部分范围并统一发行声明。这是当前文件不一致的事实，本规划不代替作者作许可证选择，也未更改许可证。
- 随包录制引擎、媒体工具、字体和下载器要固定版本、记录来源与分发材料；macOS 签名/公证和正式发布账号在发行阶段落实。
